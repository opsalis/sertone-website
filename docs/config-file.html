Config File

Set up a wrapper with a single file. Drop a btw.yaml next to the wrapper and it configures itself on start — no clicking through the console. This is how you deploy one wrapper, or a thousand identical ones, with a tool like Terraform or Ansible.

Overview

Everything you can set in the control center, you can also declare in one file. On boot the wrapper reads btw.yaml and applies it: how it reaches the network, its settings, which identity it uses, and the services it hosts. The file is the source of truth — restart the wrapper and it comes back exactly as declared.

The file has five parts, all optional:

SectionWhat it sets
wrapperNetwork & storage (where data lives, which addresses to listen on)
settingsThe same preferences you find under Settings
identityWhich persona this wrapper uses, and who owns it
servicesThe services this wrapper hosts (APIs, sites, files)
schema_versionThe file format version (use 1)

Where the file lives

The wrapper looks for btw.yaml in this order: the path in BTW_CONFIG if you set it; then btw.yaml in the wrapper’s data directory (BTW_DATA_DIR, e.g. /data) — the natural spot for a container that mounts a data volume; then next to the wrapper binary. So on a headless deploy you can simply drop btw.yaml into the mounted data directory, with no environment variable to set.

If you name a file explicitly and it is missing or invalid, the wrapper refuses to start rather than guessing — see Safety. If there is no file at all, the wrapper simply boots on its defaults, exactly as before.

wrapper — network & storage

Boot settings for the wrapper itself. These take effect on the next start.

  • data_dir — where the wrapper keeps its data (keys, encrypted stores)
  • web_listen — the address for the control center (default :3000)
  • mesh_listen — the address the wrapper listens on for the mesh
  • mesh_advertise_addr — the address other nodes should reach it at
  • bootstrap_peers — a starting list of mesh addresses to connect to
  • share_dir — a directory to serve (see services)

Anything you set here overrides the matching environment variable; anything you leave out keeps its normal default.

settings — your preferences

The same preferences available under Settings, set ahead of time. Only known, safe keys are accepted (for example spending limits, auto top-up mode, a nickname, your preferred region). An unknown key is rejected so a typo can never silently do the wrong thing.

identity — persona & owner

Two public ids — never secrets. Secrets are never written in this file.

  • persona_uid — the persona this wrapper uses. Leave it out and the wrapper creates a fresh persona on first boot (and keeps it across restarts). Set it to use a persona that is already present on this wrapper.
  • owner_persona — the public fingerprint of the persona that owns this wrapper. It lets the owner administer this wrapper remotely from any device. Leave it out and remote administration is off.

See Wallet & Personas for what a persona is. A persona’s secret key is provisioned out of band, never in the file.

services — what this wrapper hosts

A list of the services this wrapper runs. The wrapper starts each one on boot and keeps it running. Each entry has a type:

appserver — host or front an API

Serve an API to the mesh. Set exactly one of:

  • path — a backend this wrapper hosts (for example http://127.0.0.1:8080)
  • fqdn_port — an existing server this wrapper puts in front of, at host:port

Optional pay_per_use (a price in USDC per call) and subscription set the terms. Payment is always settled on-chain in USDC or USDT; the file only declares the price.

website / ftp — serve a directory

Serve a folder as a mesh-native website (type: website) or file share (type: ftp) with share_dir. Visitors reach it over the mesh under your wrapper’s name — no public IP is ever exposed.

appstore-app — run a packaged app 24/7

Run a published app continuously (app is the app’s id, with optional tracks_dir and label). Declaring an app in the config file is coming next; today, install it from the App Store and it stays running.

Safety

  • No secrets, ever. The file holds only public ids and settings. The wrapper refuses to load a file that contains anything secret-shaped.
  • Fail-closed. A file you named that is missing or invalid stops the boot — the wrapper never starts half-configured. A configured persona that is not present is refused rather than replaced with the wrong one.
  • The file wins. On restart the wrapper re-reads the file and comes back exactly as declared, so a fleet stays consistent and self-heals after a reboot with no manual step.

A full example

A headless wrapper that serves one API and one website:

schema_version: 1

wrapper:
  data_dir: /var/lib/sertone
  mesh_listen: ":3991"

identity: {}          # no persona_uid → create one on first boot, keep it across restarts

settings:
  nickname: "edge-node-01"

services:
  - type: appserver
    name: quotes
    fqdn_port: 127.0.0.1:8080     # this wrapper fronts a server already running here
    pay_per_use: "0.001"          # 0.001 USDC per call

  - type: website
    name: docs-site
    share_dir: /var/www/site      # served over the mesh under this wrapper's name

Deploy that file to a fresh machine, start the wrapper, and it comes up serving both — nothing else to do.
